# 面试讲稿：agent-memory

## 项目亮点（三段式）

**背景**：LLM Agent 的上下文窗口有限，但长期协作需要跨会话记忆。常见的单库 RAG 方案检索粒度粗糙、缺少时间维度，无法区分"上周的临时讨论"和"用户长期在乎的事"。

**方案**：一个"按天滚动的记忆传送带"——会话 → 滚动摘要（格式契约）→ 今日草稿 → 昨日日记 → 近 6 天拼装 → 长期折叠 → 四段 memory.md 常驻上下文；同时把用户画像拆成带标签的元事实存 SQLite+FTS5，供 `search_memory` 按需检索。

**收益**：近期精确、远期抽象；token 成本近似线性（水印增量 + 指纹去重 + 零 LLM 拼装）；记忆可读可改可审计；全链路离线可演示（FakeLLM）。

## 高频追问与答案

**1. 为什么不用单一 RAG？**
时间维度压缩解决"长期记忆"问题：最近的事保持精确（today/daily/week），旧事逐层抽象（longterm），一年后回看仍有效的是用户画像核心；深度记忆事实库（标签+FTS5）补足"按需检索"能力。二者互补，不是替代。

**2. 上下文窗口有限怎么控制？**
常驻上下文只有一份 ≤2000 token 的 memory.md（四段）；其余细节沉淀在摘要 JSON、daily/、facts.db，需要时用 `search_memory` 按需拉取。

**3. 成本怎么控制？**
三个手段：水印增量（只处理 delta）、指纹去重（同一批内容不重复折叠）、确定性拼装（assemble/week 零 LLM 调用）。预算还随轮数线性缩放（40 字/轮，封顶 400 字）。

**4. LLM 输出不可靠怎么办？**
格式契约单一来源：prompt 要求、写前校验、下游提取共用同一份定义；校验失败最多调一次"格式修复器"重排；仍失败则保留旧产物、记录错误、下轮重试。绝不静默丢数据。

**5. 记忆与项目文档的边界？**
记忆只收用户画像（身份、审美、兴趣、喜恶、长期关注方向），工作方式偏好、协作流程、工程规范属于项目指令/技能，不进记忆。prompt 里有明确的"抽/不抽"判别准则，宁可漏不可错。

**6. 如何保证一致性？**
脏会话追踪（summary≠snapshot）+ 提交前 revision 校验（处理期间摘要被改则放弃）+ 原子写（tmp+rename）+ 每日任务断点续跑 + 失败步骤保留旧产物。

**7. 如何演示？**
`npm run demo`：6 步（投喂会话 → 滚动摘要 → 今日草稿 → 推进 1 天出日记/周/事实 → 推进 6 天折叠长期 → memory.md + search_memory 检索）。离线、确定性、无 API key。

**8. 与原项目的差异？**
独立实现，去掉 Electron/React/Server/插件等外围；频道隔离与分支游标简化（保留数据一致性语义）；LLM 抽象为可插拔接口 + FakeLLM；新增可注入时钟便于演示与测试。

**9. 扩展方向？**
可选的向量检索（补 embedding 检索）、跨 Agent 记忆共享、遗忘机制调优（窗口大小/预算曲线参数化）、记忆可视化。

**10. 遇到过什么坑？**
三个典型：中文 FTS 检索退化（CJK bigram/trigram 补充 + LIKE 兜底）；格式契约失配（prompt 与解析器各自维护标题导致摘要被静默丢弃——用单一来源契约解决）；跨日时间歧义（摘要只有 HH:MM 而会话跨多日时 time 置 null，避免错记日期）。

## 现场演示脚本

```bash
npm install && npm run demo
```

讲解要点随步骤：

1. **滚动摘要**：指着 `### 重要事实 / ### 事情经过` 讲格式契约。
2. **今日草稿**：讲水印增量——只有 delta 进 LLM。
3. **日记/周拼装**：`compileDaily` 的指纹去重与 `assembleWeekFromDaily` 零 LLM。
4. **长期折叠**：`rollDailyWindow` 出窗折叠 + 源文件删除。
5. **memory.md**：四段拼装，常驻上下文。
6. **search_memory**：标签优先命中、全文兜底。
